# src — which module owns which invariant

Read this before grepping. Every row below is a **decision that only one module is allowed to make**; if you
need to change it, change it there and let the rest follow. Rows carry module paths and, where the symbol *is*
the invariant, the symbol — never line numbers, which rot within a week.

Two things are deliberately absent: a function inventory (the editor gives you that for free) and anything
whose owner is still contested. A wrong owner is worse than no map, so the last section lists what is
unsettled rather than guessing.

## The invariants

| invariant | owner | what it decides |
|---|---|---|
| whether a send happens | `src/adapters/policy.ts` | the policy per account, the 5-minute window, single spend, and that the `allowed` audit row is written *before* delivery; `.observe` for page-confirmed LinkedIn sends |
| whether mail approval matches the actual send | `src/mail-approval.ts`, reached only through `createSendGate.mail` | exact frozen mail binding, required pins, prepare/compatibility/require, atomic unique spend plus audit before dispatch; `src/send-approval/canonical.ts` mirrors Home's shared vectors |
| what a source is | each adapter's `source` declaration, typed by `src/adapters/source.ts` | label, icon, poll interval, page size — the one place a source describes itself |
| what a source can do | `src/adapters/capability.ts` (`CAPABILITY_KEYS`) | the vocabulary; every adapter declares every key, so a missing capability is a type error, not a runtime surprise |
| how a source delivers a message | `src/adapters/index.ts` (`createRegistry`) | one `sync`, one `media`, one `send` per account — transport differences are absorbed here, never in the gateway |
| which Gmail threads a list asks for | `src/adapters/gmail.ts` | the inbox. A mailbox that has Cora's important labels (`Cora/Important Info`, `Cora/Important Context`, `Cora/Important Draft`, `Cora/Important Sop`) or `📥 Next Brief` also lists those threads, because Cora removes the inbox label from them. A conversation archived here is remembered in `inbox_gmail_archive` and stays off the list. The cursor version is `latest-v2` in `src/sync-plan.ts`, so a list saved as inbox-only is read again |
| how many Gmail units one account may spend in a minute | `src/gmail-client.ts` | 1,500 units in a rolling minute at the published method costs, then a 60-second stop; the same stop follows Gmail's own `rateLimitExceeded`. `src/adapters/gmail.ts` answers the newest page and an open thread from the cache while the stop holds, so the panel gets no error line. A read Gmail could not accept is kept on the row (`inbox_read_hold` in `src/inbox-cache.ts`) and sent on a later sync |
| whether a Gmail credential exists, and when its access token is renewed | `src/gmail-oauth.ts` | the one 0600 record per account in the plugin data dir, the access-token cache and its expiry margin, one refresh in flight per account, and the last failure kept on the record — a `deleted_client` failure is not asked again until that record is replaced; no other module reads or writes the credential file. The account id is the mailbox address once a profile read can publish it. Until then a legacy file (`gmail-personal`, `gmail-business`) stays, refreshed with the client already stored on that file. The legacy-id map lives beside those files, not inside them. `src/gmail-login.ts` runs the loopback exchange and writes only through this module. An empty settings client disables Add. Sign-in copies the settings client onto the file it writes. A refresh keeps posting the client already stored on that file |
| where a Gmail row's face comes from, and what "no photo" means | `src/gmail-faces.ts`, reached through `src/adapters/gmail.ts` | the split that keeps a list off the network: a stored URL answers synchronously from `gmail_faces` keyed by account *and* sender address — each account has its own address book and its own grant — and an address that has never been asked is queued once, behind the draw, the first time a new email names it. The ask is the address book, not a lookup per sender: both People listings are read page by page and every queued address is answered from that one read, which is also remembered for `BOOK_TTL_MS` because a page is drawn a row at a time. "No photo" is an answer, recorded as `failed`, and neither a picture nor a miss is asked again. The panel's `onError` turns a dead picture back into initials. A refused listing is logged once, naming the missing scope, and is not asked again; before a consent the one People call is a 403, so `list()` still answers its rows with initials and no error row. The URL allowlist stays `src/avatar-url.ts`, so the store keeps exactly what Google said |
| whether a whatsapp account exists, what is in its account state, and how it is forgotten | `src/whatsapp/auth.ts` | one 0700 directory in the plugin data dir with 0600 files, AES-256-GCM blobs under a key kept beside them; a blob that will not decrypt is refused, never replaced — a fresh identity is a re-pair, and re-pairing is the ban lever. `clearAccountState` removes the two files without opening them, because a state that cannot be decrypted is exactly what a re-pair has to be able to leave |
| when a whatsapp socket exists, how long it lives, and why a start failed | `src/whatsapp/lifecycle.ts` | one socket handed to every caller (the boot service and the card ask the same question and get the same socket), opened on first ask rather than at import, closed on dispose or when the host stops the boot service, and stopped after the pairing idle window only when it never became a linked device — a linked socket is the receipt path and a timer must never close it. `ensure()` is the ask for a call that needs a live socket: a stopped one is opened again rather than turned into a dead source, and `opening()` says an open is in flight. The last refused start is kept here for the card, because credential files say an account exists and never say a socket is up, and every open, close (with its caller's reason) and WhatsApp-reported close is one recorded line |
| what a whatsapp socket does once it exists, and what it reports | `src/whatsapp/connection.ts`, with `src/whatsapp/version.ts` | connect, the 5 s → 60 s reconnect ladder, `loggedOut` as terminal, the pairing events; the version probe and its fallback constant are one decision, and the socket gets a silent logger because its info lines carry the registration payload |
| that only one whatsapp socket exists per account state | `src/whatsapp/lock.ts` | an `O_EXCL` pid lock in that same directory, released on stop or dispose: a live holder is a refusal, a dead one is stale and replaced |
| what the whatsapp transport remembers | `src/whatsapp/store.ts`, written through `src/whatsapp/ingest.ts` | the `wa_*` tables in the plugin database — messages with their raw envelope (so Baileys' `getMessage(key)` answers and a replay is idempotent), chats with the read cursor (`last_read_msg_id`, which is what "unread" is derived from and what a read mark moves forward), contacts, reactions, and chat pictures with when each was fetched; history that was synced starts read, live messages do not; `clear_cache` empties them (`src/inbox-cache.ts`) and the account state is deliberately not among them |
| where a whatsapp pairing stands | `src/whatsapp/pairing.ts` | the seven states the card draws, the four acts that change them, and that a payload past its expiry is dropped rather than offered again: an unpaired source is a state and never an error line, `logged-out` is a re-pair and not a retry, `failed` is a linked account whose socket is not up with the words that say why, and a linked device is replaced only by an explicit `unpair`. `connected` comes from a socket and never from the credential files: no socket with an open in flight is `connecting` |
| what answers a whatsapp read | `src/whatsapp/transport.ts` | the `WhatsAppTransport` seam: chat names, previews and unread derived from stored rows, one page, one chat's newest rows, and the whole store as a search corpus (`listCorpus`: every chat with every stored message, and like every other read here it opens no socket), a sender's display name, whether media has cached bytes, a chat's picture when one is stored (`avatarUrl`, a synchronous read), a read mark, a send over the socket. A read never needs the socket and a receipt only uses one if it is there; a download and a send ask the lifecycle for one, and with none the media answer is `notConnected` — a state, never a verdict recorded on the message |
| where a whatsapp chat's picture comes from, and what "no picture" means | `src/whatsapp/avatars.ts`, reached through `src/whatsapp/transport.ts` | the split that keeps a list off the network: a stored URL answers synchronously from `wa_avatars` and is not asked again. A jid with none, or a failed ask older than `AVATAR_RETRY_MS`, is queued and asked through an **already open** socket, one jid at a time, so a page of rows is a queue and never a burst of IQs. The picture query carries no privacy token (`_tools/patch-baileys.mjs`): with one, WhatsApp ignores the request and the ask times out with no link. No socket means no ask, ever: a picture is never a reason to reopen one. "No picture" is an answer, recorded as `failed` and re-asked only after `AVATAR_RETRY_MS`. The panel's own `onError` turns a dead link back into initials. The URL allowlist stays the adapter's (`src/avatar-url.ts`), so the store keeps exactly what WhatsApp said |
| where a whatsapp picture's, voice note's or document's bytes come from, and what a refusal means | `src/whatsapp/media.ts`, reached through `src/whatsapp/transport.ts` | one 0600 file per stored message under `{dataDir}/media`, named from the message id and, for a document, the extension it was sent under — a document's name, size and type are read from its envelope by `documentFacts` and a voice note's length, voice flag and type by `audioFacts`, and by nothing else; the row's `media_state`/`media_error` is the verdict and no reader infers one. A voice note is played whole — one data URL bounded by `AUDIO_LIMIT`, never a stream, never a file on the disk — so there is no range request and no eviction story; the ceiling is chosen from the declared `fileLength` a real account carries, not from what a player might like. 404/410 is terminal, 412/418 asks the phone to re-upload once through the socket, and a server refusal on media past the 14-day serve window is terminal too; a download needs the socket, so with none the request reports unavailability and neither waits nor throws. `clear_cache` empties the rows and leaves these files |
| what a failed whatsapp send means, and what the panel is told | `src/whatsapp/failure.ts`, worded by `src/adapters/whatsapp.ts` | `offline` means nothing left the machine, `terminal` means a repeat cannot change it, and `transient` — including any error it cannot read — means the outcome is unknown, so the panel says so rather than claiming a failure. One attempt per click, never a retry, and a body past WhatsApp's own ceiling is refused before dispatch |
| what a search holds, and what a hit is drawn from | `src/search-index.ts`, fed by `Adapter.searchCorpus` | membership comes from the source, not from the cache's listing: a source whose data is already on the disk answers its whole corpus (WhatsApp's `wa_*` rows through `src/whatsapp/transport.ts`, Messages' one `chats.list`), and every other source answers the cache's newest page. A corpus row carrying its own messages keeps them, so caching a thread never shrinks what search reaches; the index keeps the row behind each document, so a hit the list never loaded is answered with it (`row`). `warm()` is per-account and isolated: one source that cannot answer keeps its documents instead of emptying them |
| what the RPC surface is | `src/rpc-contract.ts` | every input and output schema; the handlers in `src/gateway.ts` are checked against it, and the panel's client is typed by it |
| what leaves for inference | `src/inference-redaction.ts`, applied by `server.ts` and `src/inbox-agent-tools.ts` | local best-effort email and phone masking for Decisions, agent tool text and mention context; names and original attachment bytes stay visible; opaque agent references live until eviction or restart; the panel and cached originals stay unchanged |
| what an agent can read and inspect | `src/inbox-agent-tools.ts` | `inbox_list` browses the cache and `inbox_search` returns ranked excerpts from `src/search-index.ts` — which reaches a source's own store, so a hit may be a conversation the cache never held, and its row comes with the answer; media references must belong to the named cached conversation; `inbox_view_attachment` returns that file and its type, and a PNG, JPEG, WebP or GIF is also returned as image content, never as text. `inbox_react` and `inbox_reply` send through `action` with `allow: 'send'`; a mention stays draft-first |
| what the panel may ask for | `src/gateway.ts` (`createGateway(deps)`) | method bodies, paging cursors, and the older-page deadline |
| whether a conversation needs attention | `src/attention.ts` | one yes/no per recent line. A score of 0.7 or more is Needed and every lower score is None. The next action is yours when their latest line still asks you, so those lines keep the highest score. Your latest line settles their asks: the conversation score is that line, and it is Needed only when the line leaves you a task you have not done. An ask you sent them is their action, and a stored score that called that ask yours is asked again. WhatsApp and Messages use an 8 second pool. A line that already has a score is not asked again. A conversation that already has scores does not reach back to older lines; the span grows only as new lines arrive, up to 32. When your last line leaves nothing to do, the conversation needs nothing. The ask carries the channel, the list snippet, and at most the last 32 stored lines, never the read flag and never a whole thread. A reply you sent is included. The list row shows that reply and sorts by its time. A LinkedIn invitation is not asked. A muted conversation is not asked, a new verdict is not stored, and the verdict already stored stays shown. The badge word is `attentionWords` in `src/attention-label.ts` |
| source refresh and freshness | `src/inbox-refresh.ts`, wired by `server.ts` and `src/gateway.ts` | backend service lifetime, per-source single flight, attempts versus live success; a network miss retries in 5 seconds and doubles up to one poll interval, and any other failure doubles up to four; `src/inbox-cache.ts` persists status and independent body timestamps |
| where a source's next page starts | `src/gateway.ts` (`olderCursor`), seeded by `sync` and advanced only by `list({ older: true })` | one in-memory cursor per source: Gmail's own `nextPageToken`, WhatsApp's row offset, Messages' slice offset into the one `chats.list` it reads, LinkedIn's own conversation cursor (`LINKEDIN_WALK_START` until the first press has learned it; that press reads the first primary page). A source that cannot page has no cursor. A failed older page forgets its cursor, except a LinkedIn read the browser did not answer: that cursor stays, and the next press retries the same page. `src/inbox-session.ts` owns the other half — the `olderRows` the owner already sees, and the deadline after which a round is given up |
| the panel's state and timing | `src/inbox-session.ts` | the snapshot, every intent, cache observation and open-thread watch, draft and attachment rules, `olderRows` |
| when the panel heartbeat runs | `src/inbox-heartbeat.ts` | one interval calls `tick`. A desktop document that is not visible does not. The phone shell does, until `pagehide`, because that webview reports hidden while the inbox is on screen. Becoming visible, `pageshow`, `focus`, and the shell `resume` event tick at once |
| a conversation's identity | `src/linkedin-conversation.ts` | urn → short key → mailbox, one spelling per conversation; `pageConfirmedConversation` in `src/linkedin-ui.ts` decides what value a row may take from the page |
| what a LinkedIn write may replay | `src/linkedin-page-session.ts` and `src/linkedin-write.ts` | the page envelope, the recorded request, and the rule that a replay needs `confirm: true` |
| the LinkedIn session's life | `src/linkedin-chrome.ts` | profile dir, prewarm, idle stop, shared operation gate; a browser a previous instance left holding the profile is adopted, not replaced or killed (`docs/bugs/2026-11-05-the-browser-outlives-the-plugin.md`); a read the browser did not answer resets the page, other list/probe failures preserve the interactive page, interactive failures reset it; the session is never exported |
| what is remembered between runs | `src/inbox-cache.ts`, `src/inbox-drafts.ts`, `src/send-audit.ts` | cached rows, stored drafts (words, never bytes), the audit table, and a LinkedIn public-profile URL keyed by conversation (`inbox_profile_link`) that a newest-page replace does not delete |
| whether a Messages chat stays read in this inbox | `src/adapters/imessage.ts` | a read mark is stored on `inbox_read_hold` through the chat's date (`through_ms` in `src/inbox-cache.ts`). A later `chats.list` keeps the dot clear until a newer message, and Messages' own unread count is left unchanged |
| the size of a draft | `src/inbox-session.ts` beside the composer | the encoded-message ceiling, not the raw byte count (`decisions/0002`) |
| what the panel draws | `src/inbox-appearance.ts`, `src/composer-mode.ts`, `src/format.ts` | bubble geometry per source, composer mode, and text shaping — not the components. A media kind's control is chosen by `MEDIA_KINDS` in `src/adapters/media.ts`: a picture or a video draws itself, a document is a chip, a voice note is an `<audio>` player whose length is the envelope's. Expired media is a line for all three, never a control |

## Where the seams are, and why

- **Panel ↔ gateway** is a typed RPC call, not an import. `src/inbox-session.ts` takes
  `rpc: Pick<PluginRpcClient<typeof rpcContract>, 'call'>`, so a renamed method or reshaped input fails `tsc`
  rather than a live call.
- **Gateway ↔ source** is the adapter registry. `account ===` branches in the gateway or the panel are a bug:
  capability or declaration decides layout and behaviour.
- **Adapter ↔ Gmail** is the `GmailTransport` factory in `src/adapters/types.ts`. `server.ts` hands out one
  `src/gmail-client.ts` client per account over the single credential store, so no adapter knows whether a
  read went over a socket or a process. **Adapter ↔ People** is the same arrangement for contact photos:
  `GooglePeopleClient` in that file, implemented by `src/google-people.ts`, so the face cache never learns
  Google's response shape (see `src/gmail-faces.ts`).
- **Adapter ↔ WhatsApp** is the `WhatsAppTransport` interface in `src/adapters/types.ts`, built once in
  `server.ts` over the plugin's store and its own socket. The adapter cannot tell a live answer from a
  stored one, which is what keeps a read working when the socket is down.
- **Page ↔ plugin** is the LinkedIn page session. Nothing else evaluates an expression in that profile.

## Unsettled — do not treat as settled

- **The panel's render decisions.** `app.tsx` still decides facts inside JSX; a view model is the named next
  step in `decisions/0001`.
- **Whether `Message` stays one union across five sources.** It is the contract's shape today
  (`src/rpc-contract.ts`), and a sixth source may force a split.
