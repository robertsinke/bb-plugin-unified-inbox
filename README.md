# Unified Inbox (work in progress)

Rail page for personal and business Gmail and WhatsAgent, opened from an inbox icon on the sidebar rail (the same place as Agent Calendar). The thread stays on the left and the message list on the right. The rail icon shows the unread count. The thread name in the chat header switches which conversation stays beside the inbox, and remembers the last choice on this browser. The arrow beside it leaves the inbox and opens that conversation as its own page. Requires local `gws` credentials in `~/.config/gws` and `~/.config/gws-inhouse`, the running WhatsAgent MCP endpoint, and — only for the LinkedIn source — an open BB browser window signed in to LinkedIn. On this machine the existing `com.robert.whatsagent-headless` launch agent runs the backend independently of its UI. The plugin only attaches to that backend and never starts or restarts it; if discovery or the process is unavailable, it fails closed rather than risking a second WhatsApp connection. The plugin server reads private messages and exposes them through BB plugin RPC; only install on a trusted BB server and trusted clients.

Currently supports the latest 20 inbox threads per Gmail account, latest 50 WhatsApp chats, reading, Gmail archive/read/unread, local WhatsAgent mark-read, 1:1 WhatsApp replies, WhatsApp photos and stickers that load as they scroll into view, and video play tiles. Gmail messages show attachment chips from cached filenames; clicking one downloads it on demand (5 MB limit). Search ranks cached threads by title, preview, sender, Gmail To/Cc, message text, and Gmail attachment filenames, matching prefixes while typing and boosting exact words over prefix-only matches; attachment contents and message bodies of unopened threads are not indexed. In WhatsApp group chats, incoming message bodies are prefixed with the sender's name, and group previews in the inbox list use the same `sender: body` form. 1:1 message headers use the contact name. List rows and the thread header show initials avatars, with group mosaics for known participants; unnamed contacts fall back to their phone number. WhatsAgent exposes no profile photos or group-member API, so groups without cached history use group initials. Cached threads are migrated from the old `WhatsApp` sender label on load. Sending a WhatsApp reply creates a proposal, then BB asks you to confirm it in the thread on the left. An agent calling the same action cannot complete the send without that confirmation. Cancelling withdraws the proposal. WhatsApp mark-read does not send a read receipt. Gmail draft controls are previews only: sending is disabled until end-to-end verification.

**Tag an inbox conversation into a thread:** type `#` in any bb composer, search by name or preview, and pick the inbox item. The `+` on an inbox row, or in an open conversation's header, inserts that same tag into the thread beside the inbox and leaves the cursor in its composer. The tag carries the conversation's latest messages to the agent when you send, plus how to act on it: a WhatsApp reply goes through the same proposal the owner confirms, and Gmail stays read-only.
**Not a complete inbox:** Gmail reply/compose, pagination, Gmail inline attachment preview, WhatsApp archive/unread, group replies, and WhatsApp audio/document playback are not implemented. While the panel is mounted and visible, it polls every 60 seconds without overlapping refreshes; WhatsAgent maintains its own connection. Sources load independently, with the first five Gmail threads shown before the full 20 arrive. Gmail list uses one API request per thread. Do not use this prototype as a replacement for Gmail or WhatsAgent.

The latest 20 Gmail thread titles and previews per account are stored in BB's plugin database and shown on reopening; these are sensitive, unencrypted local data accessible to trusted BB server users. Each successful full refresh replaces that account's cached entries; failed refreshes retain stale entries. `bb plugin rpc call unified-inbox clear_cache` clears only the plugin cache, not Gmail. Active refreshes can repopulate it. The cache is not incremental synchronization and does not provide pagination.

LinkedIn rows are DMs, InMail, and pending invitations read inside the BB browser's signed-in session. Each refresh reuses one LinkedIn tab in the BB browser, issuing the same read-only requests the LinkedIn web app makes (messaging inbox, one conversation's messages, received invitations); session cookies never leave the browser and no thread, invitation, or message is clicked or changed. Invitations show their note, or "Invitation — no note". LinkedIn is read-only: nothing can be sent, accepted, or marked read, and replies stay in Gmail and WhatsApp. If the BB browser is closed or signed out of LinkedIn, only LinkedIn fails, with one message naming it.

WhatsApp photos and stickers load on demand from WhatsAgent's loopback media endpoint when they scroll into view. Videos show a play tile and load on click. The plugin server reads the bytes with the existing local bearer token and returns a bounded media data URL; nothing is uploaded. Images are capped at 6 MB, videos at 30 MB, and audio and documents stay as text placeholders. Rendered images stay in a bounded in-memory cache, so reopening a thread does not fetch them again. The message list keeps its scroll position unless you are at the bottom, and follows the bottom while photos finish decoding.

### Local Messages (read-only preview)

Messages can list the latest 20 local conversations and open their latest 60 messages through a supervised `imsg rpc` child. Install `imsg` separately on the BB host in `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, or the host's PATH. BB needs Full Disk Access to the local Messages database; access applies broadly beyond Messages. The plugin does not install imsg, change permissions, use Photon Cloud, or disable SIP. A missing binary or denied database access affects only Messages.

Messages sending, read-state changes, outgoing reactions and threaded replies are disabled. Incoming reactions are shown where available. PNG, JPEG, GIF and WebP attachments up to 6 MB can be opened on demand; other, missing or larger attachments remain placeholders. The server rechecks the attachment against current conversation history and the local Messages attachment directory, and does not expose filesystem paths. Edited and unsent messages and the existence of reply context are indicated where supplied by `imsg`; full reply threading and edit history are not shown. The open conversation is reconciled periodically while visible, rather than relying only on insert events. Local message history and conversation metadata are stored in the same sensitive, unencrypted plugin cache described above; `clear_cache` also clears those copies, not the Messages database. This preview is not full feature parity.

Build: `npx tsc --noEmit && bb plugin build`. It is not installed automatically.

LinkedIn is not implemented. LinkedIn conversations, InMail, and invites are planned as a read-only source attached to a locally run LinkedIn MCP server; access options and their ToS/account risk are compared in [docs/research/linkedin/linkedin-inbox-options.md](./docs/research/linkedin/linkedin-inbox-options.md) and the plan is [docs/plans/2026-10-28-002-feat-linkedin-inbox-source-plan.md](./docs/plans/2026-10-28-002-feat-linkedin-inbox-source-plan.md).
