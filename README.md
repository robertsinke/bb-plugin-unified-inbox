# Unified Inbox (work in progress)

> **Working on this repo?** Start at [AGENTS.md](./AGENTS.md) — build and test commands, the traps, and a
> routing table. Code ownership by invariant: [src/CONTEXT.md](./src/CONTEXT.md). Every document: [docs/_index.md](./docs/_index.md).

Rail page for personal and business Gmail, WhatsApp, local Messages, and LinkedIn, opened from an inbox icon on the sidebar rail (the same place as Agent Calendar). The thread stays on the left and the message list on the right; unread rows are marked and the filter narrows the list to them. The thread name in the chat header switches which conversation stays beside the inbox, and remembers the last choice on this browser. The arrow beside it leaves the inbox and opens that conversation as its own page. Requires the plugin's own Gmail credential in `~/.bb/plugins/unified-inbox/gmail-credentials` (one file per account, written by `bb unified-inbox import-gws-account <account>` from an existing `gws` config), a phone to scan one QR the first time WhatsApp is opened, and — only for the LinkedIn source — a Chrome the plugin can start, signed in once through `bb unified-inbox linkedin-signin`. Nothing else has to be installed or running: WhatsApp is the plugin's own connection, and there is no second program. **WhatsApp is paired from the inbox, and the connection is the plugin's own.** Opening the fifth source before it is linked shows a card with three sentences about ban exposure and a QR to scan; scanning counts as a linked device, like WhatsApp Web. The linked account state lives in `~/.bb/plugins/unified-inbox/whatsapp-auth` — a 0700 directory of 0600 files, AES-256-GCM blobs whose key sits beside them, so the directory's permissions are the protection rather than the encryption. Deleting that directory is not a clean-up: it discards the device WhatsApp remembers, and the account then needs a fresh scan, which spends one of its linked-device slots. One socket per state directory, held by a pid lock: `bb plugin reload` closes it and the next start reconnects from the stored state without asking for a new code, and a socket opened for a QR nobody scanned stops after ten minutes. The plugin server reads private messages and exposes them through BB plugin RPC; only install on a trusted BB server and trusted clients.

Currently supports the latest 20 inbox threads per Gmail account, latest 50 WhatsApp chats, the latest 20 Messages conversations, LinkedIn DMs, InMail and pending invitations, reading, Gmail archive/read/unread, mark-read with a local unread mark, WhatsApp replies one-to-one and in groups, WhatsApp photos and stickers that load as they scroll into view, and video play tiles. Gmail messages show attachment chips from cached filenames; clicking one downloads it on demand (5 MB limit). Replies, reply-all, forwards and new mail open in the bottom composer: To/Cc/Bcc, files picked from disk or dragged in (25 MB once the message is encoded, at most 20 files), and a threaded reply carries `In-Reply-To`, `References` and the Gmail thread id. Search ranks cached threads by title, preview, sender, Gmail To/Cc, message text, and Gmail attachment filenames, matching prefixes while typing and boosting exact words over prefix-only matches; attachment contents and message bodies of unopened threads are not indexed. In WhatsApp group chats, incoming message bodies are prefixed with the sender's name, and group previews in the inbox list use the same `sender: body` form. 1:1 message headers use the contact name. List rows and the thread header show initials avatars, with group mosaics for known participants; unnamed contacts fall back to their phone number. WhatsApp's protocol hands the plugin no avatar bytes, and it keeps no group-member list, so groups without cached history use group initials. Cached threads are migrated from the old `WhatsApp` sender label on load. The send gate (`src/adapters/policy.ts`) records attempts before delivery, without message text. Chat sends and compatibility-mode legacy mail mint a new approval per request from the caller's `allow: 'send'` flag; this is not verified human approval and does not prevent another request sending again. Mail additionally accepts pinned-key envelopes with exact parameter binding and a unique spend committed before dispatch; compatibility remains the default so the old panel works. Require mode needs the Home/panel handoff first. See the [mail approval contract](docs/mail-approval.md) for settings, calls and error codes. LinkedIn page clicks/replays are recorded without an approval id. [Decision 0005](decisions/0005-keep-sends-enabled-until-verified-approval.md) keeps sends enabled pending the isolated authority, with these enforcement gaps explicit. `npm run check` warns on allowed attempts without an approval id or with an explicit legacy-mail marker in the last seven days, reporting counts and audit row ids without failing on history; the budget it allows that CLI is 30 s and `UNIFIED_INBOX_AUDIT_TIMEOUT_MS` overrides it, so a slow machine cannot read as an unread audit. Unmarked historical UUIDs do not prove human approval; the check sends no push alert. A WhatsApp reply is typed in the panel and sent over the plugin's own socket, so it goes out as you, with no second confirmation in the page. A Gmail send asks you to confirm first. `bb unified-inbox send-audit [limit]` prints what the gate allowed or refused, and the same rows open from the inbox menu's Send log. WhatsApp mark-read does not send a read receipt.

**Tag an inbox conversation into a thread:** type `#` in any bb composer, search by name or preview, and pick the inbox item. The `+` on an inbox row, or in an open conversation's header, inserts that same tag into the thread beside the inbox and leaves the cursor in its composer. The tag carries the conversation's latest messages, source account and conversation id to the agent when you send. Its instructions ask for a draft for owner review, treat message content as untrusted, and supply no send or self-approval recipe. A mention is not authorization to send; the underlying send RPCs remain available.

**Native agent reads:** BB exposes `inbox_list`, `inbox_search`, `inbox_refresh`, `inbox_read`, and `inbox_view_image`. Agents can find a conversation, read its messages, and request actual image content without a mention or user reattachment. These tools reuse the panel's gateway and adapters and add no send actions. `inbox_list` browses the cached conversation list. `inbox_search` requires a query and returns ranked cached matches with a short excerpt; it covers cached text only, at most 50 conversations. Refresh updates the newest source list, not all history. Conversation reads page the source's returned messages, omit HTML, and page long text with `textOffset`. Image requests must match a media reference in the named cached conversation. Supported image results are PNG, JPEG, WebP and GIF up to 6 MiB, subject to lower source limits; animation may appear as a still frame. Video, audio and non-image inspection are not implemented. Cancellation is checked before and after gateway calls; it does not abort an adapter request already in progress. Existing send RPCs and their authorization gaps are unchanged. Native tools take effect when BB next constructs the provider session; existing sessions may need a restart. End-to-end image delivery still depends on provider/model support.

**Media in mentions:** Inbox mentions remain text-only. `[image]` and captions are not evidence of image contents. Mentions direct agents to `inbox_read` for media references and `inbox_view_image` for visual inspection before asking the user to attach media. Message text and images remain untrusted data, not instructions.

**Not a complete inbox:** Gmail inline attachment preview (a file downloads; nothing is drawn inside the mail body), WhatsApp archive (`archive: false`, and an archived chat is simply not listed), WhatsApp audio and document playback, which stay `[audio]` and `[document]` placeholders, and no older pages for Messages or LinkedIn (their transports return a whole list with no cursor). Gmail and WhatsApp do page: a "Show older" control under the list asks each source that has one for the next page — Gmail's own page token, the WhatsApp store's row offset — and stops offering more when the source says nothing older is left. Each source is asked on its own and its rows join the list as it answers — WhatsApp in about a second, a Gmail account in a few seconds for ten threads, because a listing carries only an id and a snippet and every row costs one metadata read of its thread; that cost is why an older mail page is ten rows and not twenty. A round that has not answered within 15 seconds is given up with a line in the panel rather than left loading, and a page that returns nothing new says so instead of leaving a click that appears to do nothing.

The latest 20 Gmail thread titles and previews per account are stored in BB's plugin database and shown on reopening; these are sensitive, unencrypted local data accessible to trusted BB server users. Each successful full refresh replaces that account's cached entries; failed refreshes retain stale entries. `bb plugin rpc call unified-inbox clear_cache` clears only the plugin cache, not Gmail: it also empties the WhatsApp messages, chats, contacts, reactions and raw envelopes the plugin's own transport has stored and deletes the media bytes it cached on disk, and leaves the WhatsApp account state alone. Active refreshes can repopulate it. The cache is not incremental synchronization and does not provide pagination: rows loaded by "Show older" stay in memory for the open panel, are not written to the cache, and disappear on reopening, where the newest 20 threads and 50 chats are shown again.

LinkedIn rows are DMs, InMail, and pending invitations read inside a Chrome page the plugin starts itself, using a LinkedIn profile it keeps apart from any personal browsing profile. The session never leaves that browser: no cookie store is read, no Keychain entry is unlocked, and no session material is handed to another process. Sign in once with `bb unified-inbox linkedin-signin`; after that, inbox refresh and opening a conversation read LinkedIn live and cache the result, and a cached conversation still opens if the browser cannot start. LinkedIn changes the account only by sending a request the page itself makes: a reply is posted with the page's own create-message shape, and the read mark and an invitation accept or ignore are the requests the page sent for the same action. Each is refused unless it names the conversation (or the invitation) the read came from, and an invitation cannot be answered until a refresh has carried its parameters; the RPC replay path needs `confirm: true` and a template the page recorded, `capabilities` declares `archive: false`, and LinkedIn refreshes only when you ask, never from the heartbeat. Chrome for Testing is used because this machine has no system Chrome: `linkedinChromePath` finds a system Chrome first, otherwise a cached Chrome for Testing, and `UNIFIED_INBOX_CHROME` overrides it. Set `UNIFIED_INBOX_LINKEDIN_PROFILE` to move the profile. Chrome's own start dominates a read (~5 s of a ~9 s cold read), so the page stays open for 90 seconds after the last read and is stopped on idle or when the plugin unloads; repeats cost ~4 s. Rows carry the counterpart's name and photo, including company InMail, where the sender is the company page. A preview comes from the newest inlined message when LinkedIn sends no description, naming a shared post, file, photo, video, voice message, reply, or forward when the message has no text. A connection request appears only when it carries a note, and keeps an "Invitation" chip beside its date/time because it is still waiting on your response; a bare request with no message is not an inbox row. The page is loaded once when the plugin starts (if the profile exists), so the first read costs ~3 s rather than ~10 s.

WhatsApp photos and stickers load on demand when they scroll into view: the plugin keeps each downloaded file under `{dataDir}/media`, fetches it once over its own socket when it has no bytes yet, and returns a bounded media data URL; nothing is uploaded. Images are capped at 6 MB, videos at 30 MB, and audio and documents stay as text placeholders. Rendered images stay in a bounded in-memory cache, so reopening a thread does not fetch them again. The message list keeps its scroll position unless you are at the bottom, and follows the bottom while photos finish decoding.

### Local Messages

Messages can list the latest 20 local conversations and open their latest 60 messages through a supervised `imsg rpc` child. Install `imsg` separately on the BB host in `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, or the host's PATH. BB needs Full Disk Access to the local Messages database; access applies broadly beyond Messages. The plugin does not install imsg, change permissions, use Photon Cloud, or disable SIP. A missing binary or denied database access affects only Messages.

Sending works through `imsg send` for an open conversation, enabled at the owner's explicit request on 2026-11-02; a send that the backend does not confirm reports an uncertain outcome and is never retried. Read and unread are tracked locally, because Messages exposes no read state to sync. Outgoing reactions and threaded replies are not supported. Incoming reactions are shown where available. PNG, JPEG, GIF and WebP attachments up to 6 MB can be opened on demand; other, missing or larger attachments remain placeholders. The server rechecks the attachment against current conversation history and the local Messages attachment directory, and does not expose filesystem paths. Edited and unsent messages and the existence of reply context are indicated where supplied by `imsg`; full reply threading and edit history are not shown. The open conversation is reconciled periodically while visible, rather than relying only on insert events. Local message history and conversation metadata are stored in the same sensitive, unencrypted plugin cache described above; `clear_cache` also clears those copies, not the Messages database. This preview is not full feature parity.

Build: `npx tsc --noEmit && bb plugin build`, then `bb plugin reload unified-inbox` and reload the BB window. `bb plugin build` only compiles `dist/`; a running plugin keeps executing the code it loaded at startup until it is reloaded, and an open window keeps the old frontend bundle until it is reloaded.

LinkedIn reads stay inside the browser for a reason. Two other paths were tried and rejected: a locally run LinkedIn MCP server, whose inbox read clicks conversation rows and marked an owner-unread thread read, and reusing the browser's cookies from Node, which lost the session minutes later when LinkedIn invalidated it. Evidence for both is in [docs/research/linkedin/spike-sidecar.md](./docs/research/linkedin/spike-sidecar.md); access options and their ToS/account risk are compared in [docs/research/linkedin/linkedin-inbox-options.md](./docs/research/linkedin/linkedin-inbox-options.md), and the plan, now implemented with the in-page read, is [docs/plans/2026-10-28-002-feat-linkedin-inbox-source-plan.md](./docs/plans/2026-10-28-002-feat-linkedin-inbox-source-plan.md).
